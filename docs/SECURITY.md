# 安全政策

> **文档状态**：公开版本 **0.1.1**；当前行为以代码为准。


## 授权与锁模型

**锁（本次核心变更）**
- 锁只有两个来源：① 输入时自动上锁；② 用户在面板**手动上锁**（持久化在 owner 记录，含原因，**只能手动解除、不会自动过期**）。
- AI **没有任何锁动词**：`shell_manage action=claim` / `action=release` 已删除。AI 侧不存在“解锁”路径。
- 手动锁的覆盖面：不仅是写入 —— `close` / `resize` / `rename` / `respawn` 等改动类动作同样被拒。
- 归属（owner）是**软约定**：只表示“谁创建的”，不是权限闸门；用户明确要求即可操作他人创建（含面板创建）的 shell。

**授权（consent）**
- 授权列表只列真实、非子代理的活跃会话，优先“已授权/近期出现”，其余折叠 —— 不再铺出已归档会话。
- `/actors` 改为 SWR 缓存（TTL 5 分钟，快照窗口 120），冷启动后可命中缓存；授权变更在界面上即时反映。
- 审批与授权相关的拒绝都会写入提示信息（含原因与详细参数），并落到 `notices.json` 便于复盘。

> **本插件由 AI 开发、未经人工安全审计。** 本文件是作者自述的安全模型，不是独立评估结论；
> 请把它当作「作者认为的边界」，而不是「已经验证过的保证」。

## 开箱即用的依赖前提

装一个插件"装成功"不等于"能用"，这里把前提写清楚，缺什么插件会自己说：

| 依赖 | 谁提供 | 缺了会怎样 |
|---|---|---|
| `tmux` ≥ 3.x | **操作系统**（包管理器不会提醒） | 启动时体检发现 → 控制台 / `shell_diagnose` / `shell_open` / 面板 ⓘ 给出安装指引（Windows 需在 WSL 内运行） |
| `@deepseek-ai/{cordis,dsh-tools,schemastery}`、`react` | **DSH 运行时**（模块代理按 `dependencies + peerDependencies` 的**名字**转发到运行时自己那份） | 已声明为 **optional peer**：包管理器不会去装（否则会塞进第二份 cordis，服务/加载器不匹配），DSH 的代理机制照旧生效 |
| 权限预设 `danger-full-access` | 部署配置 | 受限模式下建会话报 `error connecting to /tmp/tmux-…`，面板与 `shell_diagnose` 会标出策略 |

一条命令自检全部前提：`./install-deps.sh --check`（只读，退出码 0 = 齐备）。

## 报告漏洞

请**不要**用公开 issue 披露尚未修复的安全问题。

首选渠道：本仓库 GitHub 的 **Security** 标签页 → **Report a vulnerability**（Private vulnerability
reporting）。该通道只对维护者可见，便于我们先修复再公开。

如果私有报告未启用，可以开一个 issue，但**只描述影响范围与复现所需的最小信息**，不要贴任何
可直接利用的载荷、凭据、内网地址或完整日志。我们会在私有渠道建立后请你补充细节。

反馈时请一并给出：DSH 版本、`tmux -V`、插件版本、以及你判断受影响的具体端点或工具。

维护者会尽快确认并给出处理计划。修复发布后会在 `README 的「当前版本」` 里注明。

## 安全模型 —— 部署前请先读这一段

这个插件的设计目标就是「让人和 AI 像人一样操作一台真终端」。因此它的**能力边界等于本机 shell
权限**，下面每一条都是有意为之的设计，不是待修的缺陷。请据此判断它是否适合你的环境。

### 1. HTTP 端点没有独立鉴权 —— 现在有「浏览器面闸门」，但仍不是鉴权

面板与宿主半通过 HTTP 通信，端点在 `127.0.0.1` 上由 DSH 的 `webServer` 提供
（默认前缀 `/plugins/shell`，含 `/list`、`/screen`、`/keys`、`/new`、`/kill`、`/resize`、`/rename`、
`/diagnose`）。这些路由**不校验任何独立凭据**。

**这一条曾是最严重的漏洞，现已按威胁模型逐条收口**（每条检查都对应一条真实可达的攻击路径）：

| 攻击路径 | 修复前 | 现在 |
|---|---|---|
| **跨站请求伪造**：你访问的任意网页 `fetch('http://127.0.0.1:3080/plugins/shell/keys', …)` 往你的 shell 灌命令 | 可以打通 —— 请求体解析**不看 Content-Type**，而跨站「简单请求」不触发预检，响应读不到但命令已经执行 | 拒绝 `Sec-Fetch-Site: cross-site`；带 `Origin` 时必须与 `Host` 同源；**写请求必须是 `application/json`**（这一条会强制预检，而本插件不返回任何 CORS 头，浏览器发不出去） |
| **DNS rebinding**：攻击者域名解析到 127.0.0.1，浏览器视为同源 → 可读终端内容、也能写 | 可以打通 | `Host` 必须是回环地址，且端口必须等于实际监听端口 |
| **本机其它进程/用户**：同机任意进程都能连 127.0.0.1 驱动你的 shell | 可以打通 | 只有部署挂了 DSH 的 `connection` 服务时才能收口（它校验浏览器会话 cookie，返回 401）；本插件自身无法区分「你的浏览器」和「本机别的程序」—— **这一条属于接受的风险，见下** |

闸门在**路由注册处统一包裹**（不是每个 handler 自己检查），所以以后新增路由不会漏。
被拒的请求会记进面板 ⓘ 的「浏览器面闸门」一行与 `shell_diagnose`，便于现场排查。

**仍然成立的部分**：这不是鉴权。任何能通过上述检查的请求（例如本机进程伪造 `Host: 127.0.0.1:3080`
并带 `Content-Type: application/json`）依旧可以驱动 shell —— 端点本身就是「等价于本机 shell 权限」。

因此：**不要把 DSH Web 端口暴露到不可信网络。** 需要远程访问时用 SSH 隧道，或放在带鉴权的
反向代理之后，并自行确认代理没有把这些路径放进免鉴权白名单。如果只想收敛暴露面，可以把
`exposeHttp` 设为 `false`（面板会失去工作能力，仅保留模型工具）。

服务绑在 `0.0.0.0`（有意对外服务）时，`Host` 无法用于判定是否本机，闸门会**降级**并在面板上
以 `⚠` 明确标出「Host 围栏不可用」—— 那条路径上 DNS rebinding 未被挡住。

### 1.5 三层防线：授权门 / 浏览器面闸门 / 审计

本插件的定位是"让 AI 像人一样操作真终端"，所以它**不试图**把任意命令执行变成安全操作。
它能做的是让"谁能发起、能到达哪里、事后能不能查清"三件事都不含糊：

| 层 | 挡什么 | 挡不住什么 |
|---|---|---|
| **模式闸门**（0.1.0 起） | **权限模式不是「完全控制」时**，插件工具一律拒绝并说明原因 —— 因为在 `workspace-write` / `read-only` 下插件 shell 里的命令不受文件沙箱约束（§3），用它就是在 DSH 权限系统上开洞 | 模式是「完全控制」之后的执行内容 —— 那个模式下用户本来就允许一切，插件不增加能力。只读工具（`shell_state` / `shell_read` / `shell_audit`）不受闸门限制 |
| **浏览器面闸门** | 跨站请求伪造、DNS rebinding 等"别人借你的浏览器"的路径（见第 1 条） | 本机其它进程；真正的鉴权仍需 DSH 的会话服务 |
| **审计**（输入流水 + 输出留痕） | "事后查不清"：谁、何时、对哪个 shell、发了什么、护栏是否拦下，全部落盘，会话关闭后留痕仍在 | 防抵赖（本机文件可改，见 8.5） |

要说清的一点：**模式闸门不是沙箱**，而且本插件**不提供逐条审批**（2.5 说明了为什么两种模式下审批都没有意义）。
在**完全控制**模式下，面板的「授权管理」退化为**可选的收紧手段**：你可以把某个对话单独限成
「只读」或「完全禁止」（默认跟随权限模式 = 完全控制），每条规则与其来源都记进审计链。

### 2. 高危命令拦截是启发式减速带，不是沙箱

`guardDangerousCommands` 用 20 条正则匹配危险形态，分成三组：

* **通用破坏**（10 条）：`rm` 根/家目录/通配、`--no-preserve-root`、`mkfs`、`dd of=/dev/`、
  覆盖块设备、fork bomb、`chmod 777 /`、`sudo`/`doas`/`su`、关机重启、`curl | sh`。
* **插件自身的命门**（8 条）：`tmux kill-server` / `kill-session`、`pkill|killall tmux`、
  `pkill|killall node`（宿主进程本身）、删除或覆盖 `~/.dsh/terminalkeeper`（审计与授权就在里面）、
  用 `find -delete` 删状态目录、`rm -rf ~/.dsh`。**这一组此前完全没有保护** —— 一个
  `tmux kill-server` 就足以把 AI 与用户的所有 shell 一起端掉。
* **发布纪律**（2 条）：`npm publish|unpublish|dist-tag|owner|token`、`git push` 带
  `--force|--mirror|--all|--tags`（不带 `backup` 远端时）。发版是维护者的决定，不该由 AI 代跑；
  往公开仓库推旧标签还可能把已撤销的版本重新发布。

它**可以被绕过**（字符串拼接、变量、写成脚本文件后执行、base64 等等），也**会误报**（正文里
出现 `sudo` 的普通文本同样被拦）。它的作用只是让「AI 手滑」变成一次显式确认，不是安全边界。
放行方式仍然是 `safety.bypassGuard: true`（旧名 `confirm` 已删除）—— 但要说清它的**真实性质**（审计报告 BUG-4）：

- 它**只是"调用方声明了风险"**，插件没有能力验证"面前有人"：`bypassGuard` 由发起调用的那一侧填写，
  完全可能来自模型自身，而不是一个人在点确认。
- 它仍然有用：把"静默执行"变成"必须先写一个显式声明"，并且这个声明**进入审计链**（事后可追）。

### 审计防篡改（2026-10 方案 1）

审计 = 每天独立 SHA-256 哈希链（防改/删/重排单条）+ **Ed25519 签名检查点链** `checkpoints.jsonl`
（每次写入对当天链头签名；检查点自身串链；可选 `auditMirror` 镜像到另一位置）。
`verify-audit` 同时校验：逐天哈希链、检查点签名/序号/前驱、当前文件与最新检查点一致、镜像一致；
保留期内文件缺失判为错误，早于保留期按策略清理只告警。

边界：能发现改/删/重排、尾部截断、删整天文件、检查点回滚/伪造；**不能**发现"文件+全部本地检查点
同时删除且无镜像"，同用户私钥可伪造签名。要更强保证：配置镜像、OS 追加锁、或外部时间戳/WORM。
- 它**不是**审批机制。真正"必须有人批准"的动作应当交给宿主的审批/权限能力，
  而不是指望这个参数。

真正的隔离只能靠 DSH 的沙箱模式与操作系统权限。

### 2.5 没有审批 —— 审批被「模式闸门」取代了

0.1.0 起本插件**不发起任何审批**（既不用自研浮层，也不再调官方 `ctx.approval.request`）。
理由很直接：在它可能出现的两种模式下，审批都没有意义。

- **受限模式（`workspace-write` / `read-only`）**：插件 shell 里的命令不受文件沙箱约束（§3），
  在这种模式下用它就是**在 DSH 的权限系统上开一个洞** —— 正确做法是**直接禁止**，而不是问一句
  "允许吗"。批准了照样是打洞，问本身就是自相矛盾的。
- **完全控制（`danger-full-access`）**：用户本来就允许任意命令（原生 bash 工具可以执行一切），
  插件**不增加任何能力** —— 没有需要保护的东西，审批同样无意义。

所以判定收敛成一条：**会话的沙箱模式不是 `danger-full-access` → 一律拒绝并说明原因**；是 → 默认放行。

判定读的是**会话真实生效的模式**（官方 `ctx.sandboxPolicy.resolve({ session })`，它会折叠
「审批过的显式覆盖 > 该会话的 sandbox/mode 事件 > 部署默认」），**不是**部署环境的
`DSH_PERMISSION_MODE` —— 后者在很多环境里根本没设（默认 `workspace-write`），
拿它当真相会把完全控制的会话误判成受限模式（实测过：插件被整体打死）。
读不到会话模式时**不拦**（fail-open，并记 `mode-unknown` 审计）：真正的权限由 DSH 强制，
这道闸门只是附加保护，误拦的代价远大于它带来的好处。

边界（避免误解）：

- 闸门**只管 AI 的工具调用路径**：`shell_read` / `shell_audit`（能力档 `read`）与
  `shell_state`（`none`）不执行命令、不构成沙箱逃逸，所以**豁免** —— 被挡住时也还能问出"为什么"。
- **面板不受闸门限制**：面板是**人**在操作自己的终端（HTTP 路径，`human: true`），
  与 AI 的权限模式无关；它照样会记审计（`human-panel`）。
面板里的「授权管理」仍然存在，但作用变成**完全控制下的可选收紧**（把某个对话单独限成只读 / 禁止），
不再有"首次询问"。

历史备注：0.4.0 中间版本曾经接入过官方审批（含"`danger-full-access` 下策略是 `never`，因此先把
会话策略切到 `ask`"这类补丁）。那套代码已随这次收敛删除 —— 在一个"要么禁止、要么无需询问"的场景里，
审批只是额外的复杂度。

### 3. 插件本身不受沙箱限制；代价是插件 shell 里的命令会绕过文件沙箱

这一节被**改写过** —— 以前的说法是「本插件要求 `danger-full-access`；在 `workspace-write`
下创建 shell 会失败（`error connecting to /tmp/tmux-1000/...`）」。**那个结论不成立**，源码与实测都推翻了它：

- DSH 的沙箱（`@deepseek-ai/dsh-sandbox`，Linux 上由 `dsh-sandbox-local` 用 bubblewrap +
  landlock 实现）是**逐条包装显式交给它的子进程**（服务定义原话：*wrap exact subprocess argv under a
  host-path file policy*）。官方 bash / pwsh 工具走的是这条包装路径。
- **本插件从不使用 `ctx.sandbox`**，也不经官方 bash 管线 —— 它驱动 tmux 用的是自己的
  `child_process`，也就是**不经过那层包装**，宿主 `/tmp/tmux-1000/` 对它照常可见。
- 那 `error connecting to /tmp/tmux-1000/...` 到底是谁报的？**沙箱里面**。bubblewrap 的
  `workspace-write` profile 里有 `--tmpfs /tmp`：用同样参数实测，沙箱内 `/tmp` 是**空目录**（0 项），
  `/tmp/tmux-*` 不存在 —— 所以在**沙箱内**跑 tmux 客户端必然连不上宿主的服务端。这是"沙箱内外看不见
  彼此"的正常现象，不是插件故障。

**真正需要记住的是另一半**：既然插件 shell 里的命令不在沙箱内，那么**使用这个插件就等于给该会话
开了一条绕过文件沙箱的通道** —— 在 `workspace-write` 会话里用本插件，命令照样能写工作区之外。
请据此决定要不要在这个会话挂载插件，而不要相信"插件只能在完全控制下用"。

授权方面（0.1.0 起）：默认档直接跟随 `DSH_PERMISSION_MODE` —— 完全控制视为用户已把会话交给 AI，
插件任意使用、不询问；其它模式则首次使用时发一次 DSH 原生审批问用户。

### 4. 输入与输出以明文留在会话里

所有键入的字符与终端输出都由 tmux 持有，并且 `shell_history` / `GET /screen` 会把它们**原样**
交回模型。这包括你在 shell 里敲的任何密码（`sudo`、`ssh`、`mysql -p` …）。

因此：不要在受管 shell 里输入长期凭据。确实需要时，用完立刻 `shell_manage action=close` 关掉该会话；
`history-limit` 调小只能减少囤积，不能改变「当前屏可被随时读走」这一事实。

### 5. 会留下一个脱离进程组的看门狗

宿主被强杀（例如 `kill -9`）时，tmux 服务端已经被 `setsid` 脱离，进程组的正常清理覆盖不到它，
所以插件会另起一个 `setsid` 守护脚本，等宿主消失后清理该 socket 上的 tmux。它的 pid 写在
`pidFile`（默认 `/tmp/terminalkeeper-watchdog.pid`，内容为 `<看门狗pid> <被监视的宿主pid>`），
服务端配置文件写在 `/tmp/<socket>-tmux.conf`。

这两个临时文件是**其它本机用户可读的**（权限随你的 umask）。它们不含凭据，但会暴露「有人在跑
这个插件」以及宿主 pid。可以用 `watchdog: false` 关掉看门狗，代价是宿主被强杀后 tmux 会残留。

### 6. 默认只碰自己的私有 socket

插件使用私有 tmux socket（默认 `-L terminalkeeper`），**不会**读取或干扰你日常使用的默认 tmux 会话。
但如果你把它指向默认 socket（`-L default` 或去掉 `-L`），它就会和你自己的 tmux 会话共享同一视图，
并能对它们收发按键 —— 那等于把上面第 1、4 条的影响扩大到你的全部终端。除非你明确想要这样，
否则保持私有 socket。

### 7. 本插件看不到的边界

它**不是**权限提升工具：管不到宿主进程能做的事之外的东西，也不会绕过操作系统权限。以哪个用户
运行 DSH，shell 就是那个用户；`sudo` 之后的权限变化完全由系统的 `sudo` 策略决定，插件只是把你
敲的密码原样转发进去。

### 8. 攻击面清单（一次彻底的过一遍）

把「谁能碰到什么」列清楚，比笼统说「权限很大」有用：

| 入口 | 谁能到达 | 能做什么 | 现在的闸门 |
|---|---|---|---|
| **9 个 `shell_*` 工具** | 只有被授权的模型（进程内调用，不经网络） | 等于当前用户的 shell | 高危命令启发式护栏；**没有**官方审批（见 2.5） |
| **HTTP 路由** | 本机任意进程；本机浏览器里打开的任何网页（CSRF/DNS rebinding） | 发按键（= 执行命令）、读屏幕、建/杀 shell | 浏览器面闸门（Host + 跨站 + JSON，见 1） |
| **`web_fetch` / 搜索等抓取到的内容** → 模型 → 工具 | 互联网上的任意页面 | 通过**提示注入**诱导模型执行命令 | 护栏只能挡明显形态；根本上取决于你是否让 AI 处理不可信内容 |
| **配置文件 / 设置页** | 能改你配置的人 | 改 `shell`、`socket` 等；`socket` 会被派生成路径并拼进 shell 命令 | `socket` 已收敛到 `[A-Za-z0-9._-]`；所有 shell 插值已加引号（见 9） |
| **面板本身** | 本机浏览器 | 与 HTTP 路由相同 | 同上 |
| **tmux 服务端 / 看门狗进程** | 同机用户可见其存在（临时文件、进程） | 无凭据；但可看到「有人跑着这个插件」 | 见 5 |

### 8.5 审计与留痕本身会落盘敏感内容

为了让"谁在什么时候让 shell 干了什么"可查，插件默认开启两层记录：**输入流水**
（`audit-YYYY-MM-DD.jsonl`）与**输出留痕**（`output/<shell>-*.log`，原样字节流）。
两者都在 `${DSH_HOME:-~/.dsh}/terminalkeeper/`，目录 0700、文件 0600。

代价必须说清：

* **留痕会把终端里出现过的敏感内容一起写下来** —— 包括你 `sudo` 时敲的密码回显、`export` 的令牌、
  程序打印的密钥。不需要长期留痕就 `captureOutput: false`；需要就 `auditDir` 指到加密卷。
* **它不是防抵赖的**：能读你 home 的进程就能改这些文件。它解决的是"事后查得清"，不是"证明没被改过"。
* 面板侧的人类输入只能记到 `panel` 粒度（浏览器里区分不到人）。

### 8.7 泄露排查（2026-09 一次完整的取证）

对四个面各扫了一遍：**仓库**、**git 历史**、**已发布的 npm 产物**、**运行时产物与本地文件权限**。

| 面 | 结果 |
|---|---|
| 仓库全文（含 docs 与脚本） | ✓ 无密钥/令牌/私钥；提交者是 GitHub noreply 邮箱 |
| 已发布产物（0.1.0–0.1.4） | ⚠ 见下：`PUBLISHING.md` 里带开发机绝对路径（**已发布的版本改不了**） |
| git 历史 | ⚠ 同样的路径字符串留在旧提交里（非密钥） |
| 插件运行时 | ✓ 不读任何凭据（只读 `DSH_HOME` 与 `DSH_PERMISSION_MODE`）；审计目录 0700、文件 0600 |
| 本地文件权限 | ⚠ → 已收紧：tmux 临时文件与留痕文件改为 `umask 077`（644 → 600） |

**已修的**：

- 仓库里那处开发机路径（测试文件里的写死路径）已改为占位符；
- `release:check` 的泄露扫描此前只覆盖 `lib/*` 与 `package.json`，**因此漏掉了会被发布的 docs** ——
  现在改为扫描**整个仓库的文本文件**，并新增主机名（`DESKTOP-*`）与 `sk-`/`AKIA` 形态；占位符

**留给你决定的**：

- 已发布版本里的那条路径字符串**在 npm 上无法修改**（版本不可变）。真正的风险不是字符串本身，而是

### 9. 配置值不会被拼成命令（`socket` 注入面）

`socket` 名会被派生成 `/tmp/<socket>-tmux.conf`、`/tmp/<socket>-watchdog.pid`，而这两个路径此前
是**无引号**拼进 `sh -c` 的（共 6 处）—— 一个名为 `dsh; rm -rf ~ #` 的 socket 就是命令注入。
两条防线都已就位：

1. **收敛**：`socket` 在配置解析处就被裁剪到 `[A-Za-z0-9._-]`（非法字符剔除，纯点号/空值退回
   `terminalkeeper`），并在面板与 `shell_diagnose` 里**如实说明改写过**（静默改名会让人找不到自己的会话）。
2. **引用**：所有 shell 插值改为单引号转义（`shQuote`），即使上层校验被绕过也无法注入。

回归测试真的执行了一次带恶意 socket 名的 `sh -c`，并断言注入标记文件**没有**被创建。

### 10. 双域输入（vault/macros）的威胁模型（0.3.0）

`{{v:键}}`（秘密）与 `{{m:名}}`（宏）把"凭据"和"可复用命令"引进了输入路径，边界必须说死：

**vault 防什么（四个可见面）**

| 面 | 机制 |
|---|---|
| AI 上下文 | AI 工具面**没有 vault 写入口**（只有 `vault-list`：键名/类型/次数）；引用展开发生在宿主 `expandForSend`，AI 拿到的所有返回（工具输出/审计导出/搜索/读屏）都经 `showText` —— 按**行身份**遮蔽注入所在的行（见下） |
| 审计文本 | input 事件记的是**原文**（`echo {{v:pw}}`），展开后的值从不进 `recordAudit`；消耗只记 `decision:consume + 键名` |
| 工具输出 | 同上，行身份登记表（会话级、上限 24 条注入、会话关闭即清） |
| 面板显示 | `/screen` 同样走 `showText`；面板「引用库」列表**不回显值**（改值 = 重新录入） |

**为什么是"行身份"而不是全局替换（0.3.1，实机压测后返工）**

0.3.0 的打码是"把值在输出文本里全字串替换"。这等于给调用方一个**包含预言机**：
发 `echo Kal` → `echo <用户>` → … 观察哪一行被遮，就能把秘密**逐字符猜出来**（实测还连坐：
值恰好等于用户名时连 bash 提示符都被遮）。0.3.1 只遮三类行：①整行恰好是秘密值
（tty 回显形态）；②整行**以值结尾**（"password: <值>" 形态——触发它必须已持有完整值，
不构成增长信号）；③含完整注入命令原文的行（命令回显）。其它行一律原样——
**猜前缀得到的是原样回显，没有任何"猜对一位"的信号可捡**。

**AI 侧「整条裸引用」规则（0.3.1，防转换外泄）**：AI 直接引用 `{{v:}}` 时整条 send 必须
只有一个引用 token（喂 stdin 密码提示的形态）；`echo`/管道/夹心一律展开层拒绝——值进入 AI 可
加工的管线后，任何变换输出（base64/rev/od）都不再是字面值、显示遮罩无从谈起。人面板输入与
宏闭环（`{{m:x}}` 内嵌 `{{v:}}`，宏体全量入封链）不受限；`submit:false` 宏嵌秘密拒绝展开。
多步拼接（先 `rev <<< ` 再裸注入、`cat >文件` 再 base64）是**已声明防不住**的形态——能同时
控制字节与提交时序者即可加工字节，防"不可信 AI 本身"请看上面的总边界。

**并发与一致性（0.3.2）**：vault/macros 的全部"读→改→写"按域异步互斥（面板 set/rm × 烧键
异步账 × TTL 过期扫描串行化），落盘 tmp+rename 原子替换——读方永远只见完整表；次数耗尽落刀处
二次检查（并发双发恰好一发一收）。CLI 属另一进程，锁不跨——原子写保证"至多旧一版、不会半截"。
留痕文件在 close 时把 `transcriptSha256+bytes` 写进 close 审计记录：删改留痕自此可证。

**「注入即焚」的落刀点（0.3.1；0.4.1 起额度用 maxUses 表达）**

次数耗尽的判定**不绑** `driver.send` 的返回值——"写已进管道但报错"的形态会把判定骗成
失败、键幸存、反复再注入（用户点破的绕过面）。落刀在**护栏通过之后、字节进管道之前**的
同步时刻：先标内存 spent 集合（并发双发只有一个能通过，窗口关死），再发送。误烧的代价是
人重录一次键；漏烧的代价是安全——所以宁误烧不漏烧。护栏**拒绝**的命令不烧（什么都没发出，
键保留）。同一键一次发送里引用 ≥2 次（含藏在宏里再明面引用、同串多份）在展开层**整条拒绝**——
旧版"重复引用不烧只记违规"本身就是一条合法的双份注入通道，已废除。

**残留的诚实边界（遮不住，也不假装）**

- 猜出**完整**秘密后的人为验证仍会撞上 ①② 的遮蔽（"整串候选验证"无法根除）——vault 的前提
  是强秘密；**用户名即密码这类串不在保护能力内**（它本来就该换掉）。
- **哈希/摘要同样算泄露**：插件**从不**存储或展示 vault 值的哈希（`vault.json` 只有值与元数据，
  次数耗尽即整条销毁、只留烧伤标记；审计记录里的 `hash` 字段是封链哈希，与秘密无关）。但**人自己**做保真
  验证时也别打印值的哈希——截断 sha256 对短弱值是秒级字典还原（0.3.1 实测：`a665a4592042`
  一眼认出是 `"123"`）。验长度可以，验哈希别留屏。
- 程序**自己打印**秘密的输出行（脚本回显、`printenv` 之类）不是注入所在行，不打码——
  按"已泄露"对待：别让秘密经过会打印它的管道。

**vault 不防什么（诚实边界）**

- **转换外泄（0.3.1 实机证实，最重要的一条）**：AI 把 `{{v:键}}` 放进**加工管道**
  （`printf %s {{v:pw}} | base64` / `rev` / `od` / `xxd` / `sed 's/./&./g'`…）时，宿主展开后
  屏上出现的是**值的变形输出**——行身份打码的三条规则（独占行/行尾/含注入原文）都只认
  **字面值**，变形行全部漏网，AI `base64 -d` 即可还原。实测：`printf %s {{v:xfil2}} | base64`
  输出 `VG9wU2VjcmV0LTQy` 直接进 AI 上下文。**结论：谁能在 shell 里引用密钥，谁就能外泄它；
  maxUses 也拦不住第一次（值已进管道，额度只是之后才扣）。** vault 的打码/计数防的是
  "顺手泄露"（审计、上下文、面板、history），不防"主动提取"——**把 AI 视为可执行任意命令的
  主体时，唯一真正的防线是别把重要凭据暴露给它的可达面**（stdin 提示形态也是"经它之手"，
  只是它拿到的是"喂给程序的字节"而非可控变量）。
- `output/` 留痕是 tmux `pipe-pane` 的**原始字节流**，在 JS 之外直写磁盘 —— 值进过 pane 就在
  留痕文件里。vault 不是磁盘加密；要收紧就配合 `--audit-lock`（chattr +a，可检测不可改）与
  整机磁盘加密，或对该会话接受"值在留痕里"的事实。
- **远端机器**：ssh/sudo 场景里值最终进了对端进程（这是它的用途）；对端日志/历史文件不在本插件
  边界内（例如远端 shell history 可能记下明文参数——用 `HISTCONTROL=ignorespace`、`sudo -S`
  走 stdin 这类习惯配合）。
- **本地 bash history（0.3.1 实测补充）**：把 `{{v:键}}` 用在**命令行**里（如 `echo {{v:pw}}`）
  时，展开后的明文会进该 bash 的历史文件（会话关掉也已在退出时落盘）。这不是打码能管的面——
  正确用法是 **stdin 提示形态**（`sudo -S` / `read -s` 类，值走程序的嘴，不进 history、不进 argv）；
  插件对两种形态的屏侧保护一致（行身份遮蔽），但 history/`ps` 是命令行形态自带的暴露面。
  用完一次性键后可定点清理：`sed -i '/<特征串>/d' ~/.bash_history`。
- 同权限本机进程（含被注入的 AI 通过原生 bash 工具）可以直接读 `vault.json`（0600 只挡别的用户）。
  vault 抬高的是"顺手泄露"的成本，不是权限边界。

**次数耗尽语义（0.4.1 现行：`maxUses` + `uses`/`remaining`）**：面板填的是**剩余可用次数**（提交时换算成
`maxUses = 已用 + 剩余`）；1 = 一次性，用掉即焚；改值**不重置**已用次数。落刀在**护栏通过后、字节进管道前**的同步时刻——不赌
`driver.send` 的返回值（"报错但已送达"骗不过它）；护栏**拒绝**的命令不烧（什么都没发出去，
键保留可再用）；同键一次发送引用 ≥2 次（含藏在宏里的第二份）在展开层**整条拒绝**。
误烧（落刀后发送真失败）的处置是人重录键——安全方向上宁误烧不漏烧。

**macros 防什么**

- **prompt-injection 持久化**：宏是 AI 可写的持久化命令，被注入的模型可能偷渡后门 —— 所以
  **写入全量进审计封链**（`event:macro` 带完整 text），面板默认展示全部宏（人能一眼看到环境里
  持久化了什么），删除同样入链。
- **宏藏危险命令**：护栏扫**展开后**文本（`guardOrRefuse` 的 scanText 通道），命中照常拦；
  但拒绝消息与审计只用原文（展开文本可能含 vault 值，不外显）。
- **放大与环**：宏不可嵌宏/裸键（只展开一层），展开上限 16KB；裸键 `{{x}}` 要求两域全局唯一，
  碰撞即拒（两域物理隔离：两个文件、两套前缀，键空间不共享）。

**多行 paste 通道**：宏展开出多行时走 `load-buffer + paste-buffer -p + delete-buffer`（临时文件
0600、用后即删、缓冲区名按会话隔离）。注意：不支持 bracketed-paste 的 TUI 会把整块当逐行输入。

**归属与接管**：`claim` 别人对话名下的会话默认拒绝（需 `override:true` + 用户明确同意）；
`release` 后 AI 写路径全拒（sendKeys/shell_run/runSteps 三处同闸门），读不受影响。

## 脱敏的预期形态与口令强度（长测报告 O1 的采纳）

**现象**：引用库的值在输出/审计里按**值**做全字替换（区分大小写），替换成 `[vault:{{v:键}}]`。
如果某个键的值恰好是**常见字面量**（实测里命中了宿主用户名），那么屏幕与报告里**所有**出现该字面量的地方
都会被换成占位符 —— 包括 `pwd` 路径、提示符、甚至与密钥无关的文本。**这不是泄漏，而是遮蔽过宽。**

**约定**：
- 见到 `[vault:{{v:键}}]` 占位符是**预期行为**，不是"引用原文残留"；
- 因此长测里"全程不出现明文密码"的判据应写作：**不出现明文值；占位符与引用原文均属预期**；
- 占位符**过宽**本身不构成安全问题，但会污染取证文本。

**建议**：
1. 引用库的值用**高熵口令**（随机长串）——既避免误伤普通字面量，也规避弱口令本身的风险；
2. 需要取证时优先用 `basename`/哈希/长度等**间接量**，不要在报告里回贴可能被替换的原文；
3. 若确有"值恰好是常见词"的需求，把它当**已知限制**记录，而不是改判据。

### 脱敏占位符的真实形态（0.1.0 核对）

代码里的遮蔽由 `lib/pure.mjs` 的 `redactSecrets` 完成：命中"像密钥的串"时替换为
**`[redacted` + 与原文等长的 x + `]`**（例如 `[redactedxxxxxxxx…]`），并额外处理跨行的私钥块
（`BEGIN [redacted] PRIVATE KEY`）。引用库的值另有 `[vault:{{v:键}}]` 形态（见上文约定）。
两种形态**都属于预期遮蔽**，不是文件损坏或显示错乱。
