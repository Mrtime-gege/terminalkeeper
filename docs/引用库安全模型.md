# 引用库安全模型（0.4.1 设计规范）

> **文档状态（2026-10-21）**：公开版本 **0.1.0**（内部迭代线 0.3/0.4 为历史编号）；当前行为以 `docs/项目文档.md` 与代码为准。


> **性质**：本文件是**规范**，描述将要实现的语义与不变式。**实现状态以代码为准**；文档与代码不一致时，
> 由 `scripts/test-docs.mjs`（文档门禁）报红。
>
> **一句话**：把「一个引用组」变成**一整段密文**；计数**必须落盘**且**不能被单侧回滚刷回去**；
> 是否被篡改/回滚靠一个**体积恒定、O(1) 读写、零增长**的**状态头**判定。
> **本地做不到"阻止回滚"**，只能「发现 + 拒绝 + 抬高成本」——这一点在末尾的诚实边界里写死。

## 0. 硬性约束（不可违反）

1. **不改 `lib/watchdog.mjs`**：它是单向租约回收器（只读 lease、无 IPC、无秘密）。
2. **不新建任何持秘密的守护进程 / sidecar**：独立进程只是把安全面搬家。
3. **加密层只插在 `readVault` / `writeVault` 之下**；`expandForSend → applyRefs → maskVaultLine` /
   `showText` **不改动**（它们操作内存值，与值来源无关）。
4. **保留全部现有安全属性**：Web 围栏、出口脱敏、防转换外泄、`0600` 与原子写、哈希链封链、
   命令净化。
5. **不引入新依赖**：只用 Node 内置 `crypto`（`scrypt` / `aes-256-gcm` / `randomBytes` / `createHmac` / `createHash`）。

## 1. 基础模型：一个组 = 一整段密文

**明文（加密前，仅存在于内存）**

```
{ v: 2, group: "A", epoch: 17, keys: { "<键名>": { value, maxUses, uses } }, ... }
```

- **键名、值、`maxUses`、`uses`、`epoch` 全部在密文内** ⇒ **解密前键与值都不可知** ✓
- 加密：`AES-256-GCM`，KEK 由 `scrypt(口令)`（模式 A）或系统服务引用（模式 B）派生
- **AAD（附加认证数据）必须绑定上下文**：`组名 ‖ epoch ‖ schema 版本`
  ⇒ 防止把**一段合法密文搬运到别的组/别的版本**（GCM 本身不防拼接）

**三条性质**

| 性质 | 由什么保证 |
|---|---|
| 改**任意一位**（密文 / IV / tag）⇒ **解密失败**（不是乱码，是明确失败） | GCM 认证标签 |
| **长度不可推断**：32B 与 64B 的值加密后**同长** | 加密前**分桶填充** |
| **条目数不可推断**：同桶内 1 个与 50 个键值对，密文长度**完全一致** | 同上（填充在**密文内**，不是外部元数据） |

**残余**：**桶的档位**仍可被推断（这是固定长度方案的固有边界）。增大档位跨度可降低信息量。

## 2. 引用组与加密模式

- 一个**引用组**含**任意多个键值对**；键值对语义**与老版本一致**（键名规则、`{{v:键}}` 引用、`uses` 语义不变）
- **每组独立加密模式**：`none`（不加密，兼容旧行为）/ `passphrase`（人持口令）/ `keychain`（系统服务）
- **未解锁的组一律 fail-closed**：拒绝引用与编辑，报错**不得回显键名或值**

**系统服务（keychain）为什么暂缓 —— 本机实测四条证据**

| 检查 | 结果 |
|---|---|
| `secret-tool`（libsecret CLI） | ❌ 未安装 |
| `libsecret` 库 | ❌ 不存在 |
| `DBUS_SESSION_BUS_ADDRESS` | ❌ 空 |
| `org.freedesktop.secrets`（真值服务） | ❌ **不在总线上** ← 决定性 |

⇒ 这是 headless 环境，**没有可借的服务**（非权限/接口问题）。实现时必须**先探测**，
不可用即 fail-closed（**绝不退回明文落盘**）；探测通过后才启用适配器。

### 2.1 默认引用组（特殊引用组：属性不可修改）

**默认引用组也是一个引用组**，但它的**属性不可修改**：本质就是「**不加密 + 落盘**」的引用组
（`mode: 'none'` + `persist: true`），用于保证该功能**开箱可用**、且不因误操作改变行为。

- **不可改名**（会连同组内键值对迁移 ⇒ 一律拒绝）、**不可改加密模式**（不能变成口令加密）、
  **不可删除**、**永不为锁定态**；新装插件即存在，排在首位，不选组时键值对进这里。
- **双层拦截**：数据层（`vault-io` 的 `setGroupMode`/`deleteGroup`/`createGroup`）与路由
  （`/vault-group-set` 的 rename）**都**会拒绝，不依赖 UI 隐藏按钮 ⇒ UI 有漏洞也改不动。
- `groups()` 返回 `{ mode:'none', persist:true, immutable:true, attrs:'不加密落盘', isDefault:true }`，
  面板据此显示「不加密落盘 · 属性不可修改」并隐藏相关按钮。
- 其它引用组仍可**自由**选择「不加密 / 口令加密」。

## 3. 计数：必须落盘，且不能被单侧回滚刷回去

**次数必须持久化**（用户拍板）。落盘之后的核心问题变成：**回滚旧文件能把次数刷回来吗？**

**三处结构 + 取最大值**

| 层 | 存什么 | 作用 |
|---|---|---|
| ① **密文内** | 该组真实 `uses` / `maxUses`（隐藏、带认证） | 正常来源 |
| ② **计数小文件** `vault.uses.json`（就地覆盖） | `entryId → uses` + `burned` + `kfp` | 回滚时**保底取 max**，并压制复活 |
| ③ **状态头**（见 §4） | `seq` + 全库指纹 | 检出「旧文件被覆盖」「同序号改内容」 |

**不变式（关键）**：

```
uses = max( 密文内 uses , 计数小文件内 uses )
```

⇒ **任何单侧回滚只能把数字变小**，另一侧仍保留高值 ⇒ **刷不回去** ✓

- **写入方向永远偏安全侧**：崩溃落在两次写之间时，允许「计数文件比分文新」⇒ **多记一次消耗**
  （宁可少给一次，不白送一次）。因此这两处**不需要定死先后顺序**。
- **每次消耗成本**：就地覆盖一行（约 20–40 字节）+ 重写该组密文，全在同一把 `withDomainLock` 内。
- **按次增长为 0**（增长只随**条目数**，不随使用次数）。

**不透明条目 id（实现落定）**：计数与烧伤表里的 `entryId` 一律为
`'e:' + HMAC(kfp, 组\0键)[0:22]`（`kfp` 为持久随机键）—— **绝不写明文键名**。
诚实边界补充：拿到整个 `vault.uses.json` 的人仍可对候选键名做**字典尝试**（HMAC 只挡直接可读 ✗）。

**烧毁与烧伤标记**

- `remaining = maxUses − uses`；`uses` **只增不减**；归零 ⇒ **烧毁**
- 归零时不删除记录，而写 **`burned` 标记**：`{ entryId, nameHmac, burnedAtSeq, reason: exhausted|destroyed }`
  ⇒ 之后**回滚旧密文想复活该键** ⇒ 撞上烧伤标记 ⇒ **拒绝**
- 烧伤表**不含明文键名**（只有 `HMAC(K_fp, 名字)`）与**不含值**

**额度（`maxUses`）语义（2026-10-24 现状）**

- 面板填的是**剩余可用次数**：提交时换算成 `maxUses = 已用 + 剩余`；1 = 一次性。
- `uses` **只增不减**；改值**不重置** `uses`（次数是托管额度，不是值的属性）。
- **没有独立的提权动作**：提高额度就是一次普通保存；把额度调到低于 `uses` 会立即烧毁。
- 已销毁的条目不能靠改额度续命（烧伤表以 `entryId` 为准）。

## 4. 状态头（B 方案）：体积恒定、O(1)、零增长、可自愈

**形态**（恒定约 64–128 字节，**不随组数/历史增长**）：

```
{ v: 1, seq: <uint64>, fp: <32B sha256(vault.json)> }
```

**放置点**：`~/.dsh/terminalkeeper/vault.head.json`（**独立文件**）。
> ⚠ **实现修正（2026-10-08）**：原计划复用审计链的锚点文件，**已被实测推翻**（混写会互相覆盖 ✗）。
> 2026-10 起审计链改用**签名检查点链** `checkpoints.jsonl`（`anchor.json` 废弃）；
> 引用库仍使用独立文件 `vault.head.json`，计数与烧伤另存 `vault.uses.json`。
更强（可选）：同步到**离机锚点**；最强（可选）：TPM 单调计数器（本机不可用）。

**写入协议**

1. 组装新 `vault.json` → 临时文件 + `fsync` → **rename 原子替换**
2. `fp = sha256(新 vault.json)`；`seq += 1`
3. **就地覆盖状态头**（临时 + rename）

**顺序不变式**：**vault 先、状态头后**（颠倒会制造"假拒绝"）。

**判定（读一次 vault + 读一次头 = O(1)，与历史长度无关）**

| 情况 | 判定 |
|---|---|
| `vault.seq == head.seq` 且 `fp == head.fp` | ✅ 正常 |
| `vault.seq > head.seq` | ✅ **自愈**：接受 vault 并补写头（只可能来自崩溃窗口；攻击者造不出合法新密文） |
| `vault.seq < head.seq` | ❌ **拒绝**（旧文件被拿来覆盖 = 回滚） |
| `vault.seq == head.seq` 但 `fp != head.fp` | ❌ **拒绝**（同序号不同内容 = 篡改） |
| 状态头缺失 / 损坏 | ❌ **fail-closed 拒绝**，提示「状态头丢失，请人工确认」 |

**可选补充（成本≈0）**：每次变更把 `fp` 的**短指纹（8–16 字符）经通知系统**告知用户，
使"三处一致回滚"也能被**人**发现。

## 5. 销毁与擦除

- **内存**：值一律以 `Buffer` 承载；销毁时**多轮覆写 + 长度归零**；**全链路禁止产生字符串副本**
  （禁止 `JSON.stringify(明文)`、禁止把秘密 `Buffer` 转成 `String` 后留存）
- **落盘**：整文件重写（原子写 + `0600`）后，对**旧文件**执行**多轮覆写再删除**
- **诚实**：`unlink` / 覆写 **≠ 物理擦除**（CoW、SSD 磨损均衡、日志、快照、云同步历史）
  ⇒ 只能称「**最佳努力擦除**」；真正不留痕需**全盘加密**

## 6. 同名键的销毁与重建

**身份是 `entryId`（随机、不透明），不是名字。**

| 场景 | 判定 |
|---|---|
| `a` 销毁后**重建** `a` | ✅ **允许**：新 `entryId`、`uses=0`、无历史 |
| 创建同名键时 | ⚠️ 命中**名字指纹**（`HMAC(K_fp, 名字)`）⇒ **必须显式确认 + 通知 + 审计 `decision=reuse`**（防"静默同名重生"骗到人与宏） |
| 回滚**旧密文**复活旧 `a` | ❌ **拒绝**（旧 `entryId` 命中烧伤表） |
| 想让新键继承旧额度 | ❌ 不允许隐式继承（新建键 `uses=0`、额度按你填的值） |

- 同一组内**不允许两个同名键**（解析歧义）；**跨组同名允许**，但引用语法 `{{v:键}}` 不带组限定
  （当前**没有** `{{v:键@组}}` 这种写法），所以存在同名时要靠命名区分，不能静默串组。
- **两种烧伤的文案要分开**：额度用尽（值未泄露）vs 主动销毁（视为可能已泄露）。

## 7. 诚实边界（不得在任何输出里声称"彻底防泄露 / 防回滚"）

1. **同机 root 或存活进程内存抓取**（`/proc/<pid>/mem`、调试器）**无法根除** —— 前提是"同进程必须注入明文"。
2. **Node 无法擦除字符串** —— 只有 `Buffer` 可控；任何一次 `toString()` 都会留下不受控副本（V8 堆、GC 迁移）。
3. **`unlink` / 覆写 ≠ 物理擦除**（见 §5）。
4. **一致回滚本地无法阻止**：攻击者若能把 `vault.json` + 计数文件 + 状态头**同时、一致地**回滚到同一历史点，
   本地**无法检测**。本地方案的定位是「**发现 + 拒绝 + 抬高成本**」；真正的阻止需要**离机锚点**或 **TPM 单调计数器**。
5. **密文回滚可重置次数** —— 只有在三处**一致**回滚时才成立（见 §3 的 max 规则与 §4 的 seq 判定）；
   审计链能**发现**痕迹，但**不能阻止**。
6. **分桶方案的残余**：能隐藏精确长度与条目数，但**桶的档位**可被推断。

## 8. 验收用例（实现后必须逐条通过）

| # | 用例 | 判据 |
|---|---|---|
| 1 | 锁定组的 `vault-list` | 不含任何键名 |
| 2 | 未解锁组引用 | 被拒，且报错**不含键名/值** |
| 3 | 单比特翻转（密文/IV/tag 各一处） | 解密失败 + fail-closed |
| 4 | 把 A 组合法密文塞进 B 组 | **AAD 校验失败** |
| 5 | 长度隐藏 | 32B 与 64B 值加密后同长；同组内 1 个与多个键值对、同桶时密文等长 |
| 6 | 计数取 max | 只回滚密文或只回滚计数文件 ⇒ `uses` 仍为高值 |
| 7 | 回滚 vault（不动状态头） | 被拒（`seq` 或 `fp` 不符） |
| 8 | 同序号改内容 | 被拒（`fp` 不符） |
| 9 | 崩在写 vault 与写头之间 | **自愈**（接受 vault、补写头） |
| 10 | 状态头缺失/损坏 | fail-closed |
| 11 | 烧毁后回滚旧密文 | 被拒（`entryId` 命中烧伤表） |
| 12 | 销毁后重建同名键 | 成功、`uses=0`、需确认、审计 `reuse` |
| 13 | 烧伤表内容 | **不含明文键名**（可机检） |
| 14 | 改额度不重置 `uses` | `test-vault-policy`：改值/改额度后 `uses` 保持不变；调低额度即烧毁 |
| 15 | **判定与写入均为 O(1)** | 读/写字节数为常数，**不遍历历史**（防退化断言） |

## 9. 落地顺序

1. **引用组数据结构 + v1 兼容迁移 + 通知**：老文件照常用；升级后**默认为老数据选择「落盘、不加密」**；
   只用**通知**告知（不做升级弹窗）
2. **计数三处结构 + max 规则 + 烧毁/烧伤标记**（次数先落盘可用）
3. **状态头 B 方案**（判定回滚/篡改，O(1) 零增长）
4. **口令加密组**（分桶填充 + Buffer 化 + 多轮覆写 + 解锁/锁定生命周期，含空闲自动锁）
5. **系统服务适配器**（先探测后实现；不可用则 fail-closed）

## 10. 实现清单（供一次执行；每项都要带夹具）

> 原则：**新逻辑放进新模块 `lib/vault.mjs`**，`lib/index.js` 里的 `readVault`/`writeVault` 退化成薄封装
> ⇒ 满足约束「加密层只插在 readVault/writeVault 之下」，且不让 `index.js`（已 370KB）继续膨胀。

### 10.1 服务端（逐文件）

| 文件 | 改动 | 关键点 |
|---|---|---|
| **`lib/vault.mjs`（新建）** | 数据模型与全部不变式 | `Group = {v,group,epoch,keys:{k:{value,maxUses,uses}},rev}`；`serializeGroup()`→**Buffer**（禁止中间 string）；`padBucket(buf)` 分桶；`sealGroup(buf, kek, aad)` / `openGroup(ct, kek, aad)`；`aadOf(group, epoch)`；计数 `usesOf(entryId, ctUses)` = `max`；`burned` 标记与 `nameHmac` |
| **`lib/statehead.mjs`（新建，可并入 vault.mjs）** | 状态头协议 | `readHead()` / `writeHead({seq,fp})`（临时+rename）；`judge(vaultSeq, headSeq, fp, headFp)` → `ok|heal|rollback|tamper|nohead`；**写入顺序 vault 先、头后** |
| **`lib/index.js`** | `readVault`/`writeVault` 改薄封装：调 `vault.mjs` 读取/写入，**每次变更走同一 `withDomainLock('vault')`**；`spendVaultOnSendAttempt` 内改为「解密组→递减→重封→写盘+写计数+写头」原子序列 | 不改 `expandForSend→applyRefs→maskVaultLine/showText` |
| **`lib/config-local.mjs`** | 引用组设置 | 已不再有 `vault.*` 配置键：组/模式/额度都在面板与 `vault.json` 里 |
| **`lib/pure.mjs`** | 仅新增**纯函数**：`bucketSizeFor(n)`、`nameHmac(kfp,name)`、`remainingOf(maxUses,uses)`、`judgeText(verdict)`（文案） | 便于离线夹具 |

### 10.2 迁移（v1 → v2）

- 读 v1（键名/值明文）⇒ 在**首次写入时**转成 **一个默认组**（`persistMode:none`，保持既有行为）
- **只发一条通知**（不做升级弹窗）：如「引用库已迁移为引用组，当前为不加密落盘；如需加密请在设置中开启」
- 迁移后**立即写一条初始状态头**（避免"首个快照之前无法检测"）

### 10.3 面板（`lib/client.js`，客户端半边 ⇒ 改完需刷新页面）

| 位置 | 改动 |
|---|---|
| **引用库页** | 改为**组列表**：每组一行（组名 / 模式 / **锁定态** / 条目数——锁定组不显示条目数与键名） |
| **解锁交互** | 口令输入：**掩码 + 不落 config + 不入审计**；锁定态下引用库页只显示组信息 |
| **条目表** | **仅解锁组**显示键名与值（值默认掩码，可短时查看）；显示 `remaining = maxUses − uses` |
| **编辑** | 改值（**不重置次数**）/ 改 `maxUses`（**提次需确认**）/ 重置 `uses`（**提权确认**） |
| **跨组迁移** | 需**源组与目标组同时解锁**；跨模式 = 解密 → 按目标规格重新加密（重新分桶） |
| **重建同名键** | 命中名字指纹 ⇒ **确认弹窗**「该名字曾于 … 被销毁，重建后引用 `{{v:键}}` 将指向新值」 |
| **通知** | 迁移 / 锁定 / 烧毁 / 回滚检出 / 提权 都走既有通知系统；每次变更可附**短指纹** |

### 10.4 夹具与门禁

### 10.5 一次执行的顺序（内部仍按此顺序，避免返工）

### 11.2 §8 十五条验收对应

### 11.3 必须人工实测的部分（诚实边界）✗

自动化夹具覆盖的是**纯层与静态面**；下面这些只在**真实浏览器**里成立，需人工实测（用户按计划统一测试）：

- 组栏渲染、锁定徽标切换；口令掩码输入并解锁/锁定；
- 「重建同名」的两步确认（第一次点进入确认态，第二次才写入）；
- 行内**跨组迁移**下拉（含服务端两组解锁的硬校验）；
- 主题与透明浮层（已全部改用 `--dsw-alias-*` 令牌）。

**生效方式**：服务端改动 ⇒ **重启 dsh**；客户端改动 ⇒ **刷新页面**（无 `dev:web` 时不自动热更新）。
