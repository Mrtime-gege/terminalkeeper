# 引用库安全模型

> 引用库（vault）存放"人录入、AI 只能引用键名"的秘密。本文写清楚它防什么、怎么防、以及**明确防不住什么**。

## 1. 目标与信任边界

- **值只在宿主与本机**：面板/CLI 写入，AI 侧只能拿到"键名 + 额度"，拿不到值。
- **AI 不是可信方**：它可以在 shell 里执行任意命令，因此任何"AI 看不到"都必须由**架构**保证，而不是靠提示词。
- **本机同权限进程不在防线内**：0600 只挡别的用户；磁盘未加密时，能读数据目录的进程就能读引用库。

## 2. 数据模型

- **组**：每个引用组独立加密，三种模式：
  - 不加密（明文落盘，仅防误传）；
  - 简单混淆（设备密钥，只防明文被全盘搜索/顺手抄走）；
  - 口令加密（AES-256-GCM，口令只在内存，重启后需重新解锁）。
- **条目**：键名、值、组、类型、备注、有效期至、额度。
- **额度与次数**：`maxUses`（-1 = 不限）、`uses`（只增不减）、`remaining = maxUses - uses`。
  面板填的是**剩余可用次数**，提交时换算成 `maxUses = 已用 + 剩余`；**1 = 一次性**；归零即销毁。
- **锁定组**：不列键名、不可引用、不可迁移；先解锁再操作。

## 3. 落盘格式（防"读文件直接拿到秘密"）

- **一整段密文**：基本模型是「整组 = 一段密文」——组内所有条目一起加密，**不得**逐条单独加密落盘；文件里看不到条目结构。
- **AAD**：加密时绑定组名与代际（epoch）——把密文从 A 组挪到 B 组、或用旧代际冒充，都会解密失败。
- **分桶填充**：明文按固定档位补齐后再加密，密文长度只暴露"落在哪个档"——**长度与条目数不可知**。
- **max计数**：已用次数在独立计数文件里按 **max(文件值, 内存值)** 的规则合并——计数取最大值的规则保证崩溃/并发写入不会把次数变小。
- **entryId 与烧伤表**：销毁的键只留不透明 `entryId` 与名字指纹（HMAC），**不含明文键名、不含值**；
  回滚旧密文想"复活"已销毁的键会被烧伤表拒绝。
- **状态头**：记录单调 **seq** 与指纹，写入顺序是"先数据、后状态头"；缺失/回滚/篡改都能被判定，
  崩溃窗口内可自愈。**判定/写入成本断言**：读取与写入均为 O(1)，不遍历历史条目。
- **禁止性表述**：不得用空库覆盖损坏文件、不得静默重建同名键、不得把未解锁组的键名列给 AI。

## 4. AI 侧的引用规则

- 只允许**整条裸引用**：整条输入就是 `{{v:键名}}`（典型是喂 `read -s` / `sudo -S` 这类 stdin 提示）。
- **嵌进命令会被拒绝**：`curl -H "…{{v:key}}"`、`echo`、管道等一律不发——值一旦进入 AI 可加工的管线，
  base64/rev/od 之类的变换输出就能绕过打码。
- 同名重建：销毁过的键名重新创建需要显式确认（`reuseName:true`，面板上是两步确认），防止"静默同名重生"。
- 未解锁的组：引用会得到"键可能在未解密组里"的可行动提示；口令组必须先人工解锁。

## 5. 打码与它的边界（诚实边界）

- 输出里出现值的字面量会打码；但**转换外泄防不住**：`printf %s {{v:x}} | base64`、`rev`、`od` 等
  变形后不再是字面值，AI 可以自行还原。**谁能在 shell 里引用密钥，谁就能外泄它**——额度只能限制次数。
- 终端留痕（`output/`）是原始字节流：值进过屏幕就会进留痕。引用库不是磁盘加密。
- 本机 shell history 可能记下展开后的明文（命令行形态）；正确用法是 stdin 提示形态。
- 同权限进程可直接读数据目录；引用库抬高的是"顺手泄露"的成本，不是权限边界。

## 6. 审计

- 引用库的增删改、引用消耗、解锁/锁定、组模式变更、跨组迁移都进审计链（只记键名与结果，不记值）。
- 删除条目会留烧伤记录；审计链可校验，签名检查点可异地镜像。

## 7. 明确不防的

- 主动提取：AI 只要能在 shell 里引用值，就能把它变形外泄（见 §5）。
- 短弱秘密：`123`、用户名即密码这类值不在保护能力内。
- 已拿到本机同等权限的攻击者。
- 未启用磁盘加密/未加锁的数据目录被离线拷走。
