# 贡献指南

## 仓库形态（先看这个）

本仓库是**发布仓库**：只包含运行时代码与文档。维护者日常开发在另一个私有仓库里，那里有完整的测试夹具、
构建与发布脚本；这些**不会**公开，也不会随 npm 包发布。

这对贡献意味着：

- **欢迎**：bug 报告、文档纠错、可复现的最小修复补丁、兼容性问题；
- **不在本仓库**：维护者的测试套件、开发工具与内部设计记录 —— 所以 PR 里不需要、也不应该附带这些；
- 涉及行为变更的 PR，请先开 issue 描述**问题与期望**，维护者会在开发仓库验证后再同步过来。

## 提 Issue

用仓库自带的模板（Bug report / Feature request）。请附：

1. 复现步骤（命令或工具调用参数，**不要贴任何密码/令牌**）；
2. `terminalkeeper doctor` 与面板「详情 → 运行」里的环境信息；
3. 相关审计记录（可打码，但保留 `event` 与错误码）。

安全问题**不要**开公开 issue：走仓库 Security 页的私密报告（Security advisories）。

## 代码约定

- **纯函数优先**：能放进 `lib/pure.mjs` 的逻辑不要耦合 tmux/文件系统；参数解析集中在 `lib/args.js`。
- **客户端**：`lib/client.js` 里用 `h()` 构造节点；颜色只用 `--dsw-alias-*` 主题令牌，不写死色值。
- **文案**：面向用户的提示用「人话（错误码 X）」；宿主错误码原样保留、不翻译。
- **风格**：无分号、两空格缩进、单引号；不要引入新依赖（运行时零依赖是设计目标）。

## 文档约定

- `docs/参数定义.md` 由 `lib/param-spec.mjs` **生成**，不要手改；参数变更请改 spec 并重新生成。
- 正文面向使用者：先讲"怎么用"，再讲"边界"；不要写内部提交号、构建号、会话 id 或个人路径。
- 文档里的命令与路径必须真实可用（发布前的文档门禁会核对）。

## 提交与 PR

- 一个 PR 只做一件事；提交信息写**为什么**，不只是"改了什么"。
- **不要改版本号**——发版由维护者统一处理（见 [PUBLISHING](./PUBLISHING.md)）。
- 不要在仓库里提交任何密钥、令牌、个人邮箱或本机绝对路径；维护者会在合并前跑泄露扫描。

## 行为准则

保持技术讨论、就事论事；不人身攻击、不刷屏、不提交与项目无关的内容。
